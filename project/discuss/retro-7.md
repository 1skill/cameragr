**结论：方向基本正确，但“审核闭环写好”说得过满；当前仍是待联调版本。** 本次只读文档与代码，未改文件、未验证线上或真机，未收到可核对的附图，因此不作视觉验收结论。

1. **诚实复盘：五项里，功能风险大于美术风险**

   - **C2a：认证骨架成立，真实 Apple 闭环未完成。** 缺密钥时服务端仍允许不交换授权码就发会话，这是开发过渡逻辑；生产必须检查密钥齐全，不能静默降级。
   - **C3d：改回 v4 的方向正确，但完成标准没兑现。** 蓝图要求“翻页时可分开”，进展记录实际采用淡出。可以接受为 v1 简化，但应改蓝图，不能两种口径同时标完成。
   - **C3e：符合决定。** 社区居中、操作归组、黄色签归“关于 Koco”，没有必要再重做导航。
   - **C2b 最大风险：打卡事实、资格与删帖可能不同步。** `moderate()` 先写公开与打卡，再另写达标资格，中途失败可能漏记；`deletePost()` 只在帖子仍为 `public` 时回收当天，**批准→隐藏→一小时内删除**会绕过规则。它还按时间批量删资格，缺少资格与有效打卡的明确关系。
   - **C2c+C6 最大风险：通知尚不存在。** `report()` 只写 `alerts`，没有邮件发送、失败重试与送达状态；补域名和邮箱后仍需开发。所谓“用量告警”目前也是投稿量、帖子数等估算，不能写成真实额度监控。
   - **图片权限还要补验：** 待审图使用可转发签名链接；管理员链接只凭签名中的管理员标记读隐藏图，不重新检查管理员会话。不能把它描述成“只有当前授权本人可看”。
   - **文档已漂移：** API 仍写删帖不撤打卡、旧上传参数；蓝图 C5 仍写“公开发布成功计一天”。都应统一为**首次批准当天计入，批准后一小时内删除按规则回收**。

2. **下一步排序：本地 Worker 回归 → C5 → C7 → 发布收口**

   **我不同意当前把 C7 排在 C5 前面，也不同意把剩余问题全部归为“等用户”。**

   1. **先补本地 Worker 集成测试和部署清单。** 使用本地 D1/R2、可控时钟、模拟 Apple 响应，覆盖真实路由、迁移和失败恢复；Swift 假后台测试不能证明 Worker 正确。重点测并发重复投稿、重复批准、跨午夜、删除回收、隐藏图权限、删号重建。
   2. **再做 C5。** 它完成“拍摄→投稿→批准→得卷→继续拍”的核心循环，并兑现“不做小册”。目前客户端有领奖请求，Worker 却没有对应领取路由；这比增加互动入口更基础。左页“我的”放连续天数、审核中提示和三档领取凭证，右页继续只放照片。
   3. **然后做 C7。** 复用已经稳定的审核、举报、封号与通知机制，避免另造一套不一致的权限。
   4. **生产假登录/假用户退出应立即做门禁。** 当前 `apiBase=nil` 会回退假后台并自动登录，未限定 DEBUG。Release 配置缺失应明确显示社区暂不可用，不能生成虚构社区。

   **部署当天按以下顺序验收，前一步不过就停：**

   - 备份 D1，演练旧库迁移；核对新增列、唯一索引、密钥、定时任务和管理员账号。

   - A 投稿：A 可看待审，B 不可见；断网、重启、重试只产生一帖。
   - 管理员批准：B 可见；批准当天只算一次，跨日与重复批准不多算。
   - 测一小时删除、先隐藏再删除、多帖保留当天、达标后断签领取、删号重建不能再领。

3. **留言 v1：照片背面的短留言，统一先审**

   - **样子与路径：** 抽出照片后，信息卡下接一张简洁留言纸，显示作者、正文、时间和“写留言”；长内容在详情内滚动，不挤进照片墙。入口保留可读文字，不只放图标。
   - **范围：** 仅一级纯文字，每条最多 **120 个 Unicode 字符**；无回复树、@、图片、链接、留言点赞。先做分页和明确限流。
   - **审核：** 提交后仅本人和管理员可见，批准后公开。**不赞成“命中词过滤，其他直接公开”**，否则同一张照片上出现两套公开标准。
   - **过滤：** 服务端统一长度、空白与字符规范；明显违规提示修改，其余进人工队列。覆盖五语，不能只复用当前少量中英文词表。
   - **举报与删除：** 复用邮件通知和处理记录；留言者、管理员可删，照片作者可移除自己照片下的留言。拉黑后互不可见；母帖隐藏或删除，留言同步退出公开展示。
   - **通知：** v1 只做 App 内未读提示，点入对应照片；本人可查看“审核中／未通过”。暂不做用户推送。留言不计打卡、不发奖励。
